# AGENTS.md: Laser Frame Studio

Read this first. It is the hand-off guide for any AI assistant (Claude, Codex,
Copilot, Gemini …) or developer picking up this project. Keep it up to date:
when you change something notable, add it to **History** at the bottom.

## What this is and who it's for

A browser app that converts a sequence of animation frames (JPG/PNG) into an
ILDA `.ild` file for a **LaserCube Ultra 7.5W** run by **LaserOS**. It is used by
JUMP (Jack's Urban Meeting Place) staff and by workshop participants, many of
them non-technical, who draw a few frames and want to see them on the laser.

The project owner previously had to go through Adobe Illustrator and had no
reliable frames → `.ild` converter. That is the problem this solves.

## Ground rules (please keep these)

1. **No build step, no dependencies, works offline.** The page must work by
   double-clicking `laser-frame-studio.html` (a `file://` URL). That is why:
   - scripts are plain `<script src>` files, not ES modules (modules are blocked on `file://`);
   - all scripts share the global scope, and are loaded in dependency order;
   - the sample animation is embedded as base64 (`js/sample-fox.js`), because
     browsers won't let a `file://` page read pixels from local image files.
2. **Human-readable code comes first.** The owner wants anyone to be able to
   read and edit it. Descriptive names, a header comment in every file
   explaining its job, comments that explain *why*. Prefer clarity over cleverness.
3. **Open source, MIT License** (`LICENSE`). Keep the footer credit line
   ("Built with Claude Code …") and update the version numbers in the footer,
   `README.md` and History when you make a release.
4. **Privacy:** images never leave the browser. Don't add uploads, analytics or CDNs.
5. **Plain language in the UI.** Users are artists and kids, not laser technicians.

## Draw an animation (drawing pad), v1.4

- The pad (`#drawView`) replaces the studio view (`#studioView`) in the main area
  while it's open. It's a dark canvas the same shape as the wall canvas (600 px wide).
- **Strokes are stored as vectors:** `{ rgb, pts, closed }`, with a fixed line width,
  because the laser has only one line width. A stroke that ends near its start
  becomes a closed loop.
- **Tools:** 9 laser colors (`DRAW_COLORS`), a pen, an eraser (removes whole lines),
  undo, clear frame, copy frame, blank frame, delete frame and a play preview.
- **Onion skin:** 0–3 earlier frames in faint blue, fading with distance, plus an
  optional next frame in faint orange.
- **"Use these frames on the laser"** renders a paper-style picture of each frame (for
  the thumbnail and source view) and calls `loadDrawnFrames()` in app.js. That function
  replaces the studio's frames, asking first if there were uploads, and sets Color to
  "use colors from image or drawing".
- **No tracing for drawn frames:** they carry `frame.drawing`, so `traceDrawing()` in
  trace-frame.js turns strokes straight into paths. It applies only light smoothing
  and simplification, and there's no mask. Lines match the drawing exactly, and
  in-betweens match well, because each stroke is one path in every frame.
- **Autosave:** the drawing is saved to `localStorage` (`laserFrameStudio.drawing`) on
  every change and restored on load. "Start over" clears it, after asking.
- **Tested (2026-11-11), in the browser only:**
  - Mouse drawing, colors, eraser, copy frame, onion skin (both directions) and undo.
  - Reload restore, sending to the laser (colors kept, nothing outside the canvas),
    in-betweens and a valid export.
  - Fits a phone screen.
  - Not yet tested with a touch screen or stylus, or on the laser.

## How it works (pipeline)

```
frame image
  → getWorkingImage()   resize so the longest side = "Detail" px, on white
  → toGrayscale → boxBlur → otsuThreshold/threshold → makeInkMask → removeSpecks
  → tracer by Art style:
        outline     traceOutlines()          closed loops around ink areas
        centerline  traceCenterlines()       skeleton → one line per stroke
        auto/Mixed  splitByStrokeWidth()     thin pieces → centerline, wide blobs → outline
  → smoothPath → simplifyPath → sampleLineColor          = frame.trace
  → buildLaserFrame(): pixels → ILDA units via pictureToLaser() (fitted inside the
        wall canvas box when "Fit" is on), orderPaths (nearest next),
        generateLaserPoints (spacing, corner holds, blanked jumps with holds),
        auto-coarsen spacing to fit Max points          = frame.laser
  → writeIldaFile()                                        = .ild download
```

- Settings marked `data-stage="trace"` re-trace all frames (debounced, in the
  background, current frame first). `data-stage="laser"` only rebuilds laser points.
- Pixel-based sliders are defined at a 400 px reference size (`REFERENCE_DETAIL`)
  and scaled with Detail, so they mean the same thing at any detail level.
- Each laser frame starts where the previous one ended, so jumps between frames are short.
- **Play list** (`state.playList` in app.js): what plays and exports. It holds the drawn
  frames in order, with any in-betweens slotted in after each one. `state.position`
  indexes it. Preview, slider, filmstrip, playback and `writeIldaFile` all use it.
  Drawn entries read `frame.laser` live (via a getter); in-between entries own their laser.

## Smooth motion (in-betweens), v1.3 prototype

- `makeInbetweenTraces(traceA, traceB, count)` in `js/inbetweens.js`:
  1. It matches lines between the two frames by how far their points would travel,
     using greedy best-first pairing. Loops only pair with loops.
  2. It resamples each pair to equal point counts and aligns them (flip, and a
     start shift for loops).
  3. It interpolates the pairs. Unmatched lines shrink and dim away, or grow and
     brighten in, using `path.brightness`, which laser-path.js applies.
- If less than 60% of the line length matches (`MIN_MATCHED_SHARE`), that pair gets
  no in-betweens and plays as a cut (✂ in the filmstrip). Results are cached per frame
  pair (`frame.inbetweenCache`), and in-betweens are cleared while re-tracing.
- **Tested (2026-11-05):**
  - Simple shapes (moving ball, tilting rectangle, rolling wave) morph cleanly.
  - On the fox sample, the head, back and tail morph well, but the **legs break into
    pieces**. Centerline tracing splits strokes at junctions differently in each
    frame, so segments don't correspond.
  - Possible improvements: join segments into longer strokes before matching, or
    match whole connected pieces.
- **Not yet tried on the laser.**

## ILDA / laser facts we rely on

- Format 5 = 2D true colour. Point = X int16, Y int16 (big-endian, Y up),
  status byte (0x80 last point, 0x40 blanked), then **B, G, R** (blue first).
- The file ends with a header whose point count is 0.
- LaserOS plays format 5 fine (confirmed on hardware). It asks for the fps when
  importing an animation, so animation speed is normally set there, not in the file.
  "Hold each frame" (repeat frames in the file) is only a fallback.
- Default holds and spacing were compared with the official ILDA sample files
  (`../Reference ILDA files/extracted`, from ilda.com) and the professional
  `GHOST.ild` animation: pros use ~500–1,200 units between lit points and runs of
  ~5–8 repeated points at corners and jump ends. Our defaults: spacing 700,
  corner hold 3, blank hold 6.
- A frame of ~650 points at 30k points/s redraws at ~45 Hz. Under ~20 Hz flickers.

## The install site and the wall canvas

- The outdoor show projects onto a **tall, dark wall panel** with a glass atrium on
  the left and a lit glass elevator tower on the right. The laser is mounted low and
  to the right, on a column of a nearby building. Photos and videos are in
  `../Site Images and Videos/` (`Canvas_mid_distance.jpg` shows the throw in pink).
- **The safe area ("wall canvas")** was measured from the boundary show used on site,
  `IFF_animations.ild` in LaserOS's imports folder. Its lit points span
  x −17.8k..+19.8k and y −28.3k..+30.7k ILDA units, which is about 57% × 90% of the
  full range, centred +1.5% right and +2% up. Its shape is about 2 wide × 3 tall.
  LaserOS `config.ini [setup]` had `zoom=58` and `rotZ=-24`. If those change, the
  real canvas moves.
- In the app, the "Wall canvas" group holds these as % sliders (the defaults are
  in the HTML and in `WALL_CANVAS_DEFAULTS` in app.js; keep both in sync). With
  "Fit art inside the wall canvas" on, art is contained in the box and Size is a %
  of the box. Lit points outside the box are counted (`laser.outsideCount`) and shown
  as a red warning. Canvas settings are remembered in `localStorage` (inputs marked
  `data-remember`). The page still works if storage is blocked.

## How to test

1. **Quick manual check:** open `laser-frame-studio.html`, click "Try the fox
   sample animation", play it, download the `.ild`.
2. **Check a file:** `python tools/ilda_inspect.py path/to/file.ild` and compare with
   `../Animations/Fox Test/Fox.ild` (similar point counts, holdRun ≈ 5, valid headers).
3. **Browser automation:** browser tools often can't script `file://` pages, so serve
   the folder: `python -m http.server 8765 --bind 127.0.0.1` from this folder, then
   open `http://127.0.0.1:8765/laser-frame-studio.html`. The page exposes
   `window.LaserFrameStudio` (`state`, `addFrameFiles`, `loadSampleAnimation`,
   `readSettings`, `rebuildAllLaserFrames`, `writeIldaFile`) for scripted tests.
4. The final test is always the real laser. Ask the owner to try it.
